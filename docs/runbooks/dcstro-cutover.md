## Required capabilities and the blockers that remain

These replace the earlier list of choices. Each is a capability this branch adds, or a surface that cannot be observed today and therefore makes an import fail closed.

- **Schedules** are indefinite weekly rules with dated exceptions, computed for a requested civil-date window; inactive batches are preserved inert. Rollback between batches is not an owner command in this build, and the owner-only command manifest does not change.
- **Briefings and preferences** honor per-slot enablement, the weekend choice, the lookahead window and the captures, GitHub and weather sections, only for the imported owner and only when the profile selects imported preferences. Frozen config wins; a disagreement with an explicit configured value is a conflict the importer reports and refuses. AI wording of a briefing is not supported and an active preference for it is refused. A weather section needs an explicitly configured location.
- **Tasks and reminders** keep state, explicit timed or all-day intent and the per-task reminder policy through Done, Edit and Snooze. Source priorities or categories Ducky cannot represent fail validation.
- **Watch targets** are notification-only, independent of the engineering allowlist, capped at a fixed public 1000, and observed within 20 read calls per tick and 2400 per rolling hour. Throughput is a budget; no fixed full-sweep latency is claimed.
- **The real watch reader** (ADR 0031, owner-approved 2026-10-14) reads release publication, closing times, reviews and the typed event surfaces through seven exact GET-only `gh api` shapes. It is off by default (`DUCKY_ASSISTANT_WATCH_READER_ENABLED`) and its completeness, latency and quota behavior on the real selection are unproven; enabling it waits for runtime eligibility (issue 8). Repository discovery, the source's 40-target recency-limited poll cycle and the global monitoring switch are implemented and unit-tested but have never run live, discovery stays off until an operator names the account that is the owner, there is no owner control to resume a paused switch (an operator import states it), and multi-page completeness is unproven: the residual gaps in ADR 0031 are required blockers. An import whose watch category needs a surface the configured reader cannot observe is refused and reported; a synthetic reader is not evidence of a live bridge.
- **Unsupported source behavior is a required parity blocker, not an exclusion.** Full parity is settled, so each of these stays blocking cutover and retirement until Ducky supports it: AI wording of briefings (the `urgent` priority and task categories are now carried, ADR 0032), meals (preferences, history and the briefing behavior; they are not one of the issue's listed categories but are source behavior the owner has), a control to resume a paused global watch switch (the switch itself is carried over and gates reads), the requested-changes alert's "areas mentioned", a Discord control for rolling the schedule back between batches (the service exists, ADR 0032), repository discovery and the 40-per-cycle polling coverage (implemented, unproven live), and overlap suppression against the ordinary `github_watches` DM. (Late reviews at exactly the cursor are now reconciled by review id once the boundary is known; unit-tested only.) Until then the importer refuses the corresponding input; that refusal is the fail-closed form of the blocker. The authoritative list is `docs/CURRENT_STATE.md`.

## Upgrading, and scratch databases

- **Stop the coordinator before migrations.** Migration 29 adds the runtime lock, and a coordinator from an older build does not know it, so the lock cannot protect against one. Stop it, back up, migrate, then start the new build; never run an older build against a migrated database.
- **Recreate scratch databases.** Migration 29 was revised before it was published (checkpoint boundary flag, event surface and hold columns, lock identity columns). A scratch or rehearsal database that was migrated to 29 from an earlier revision of this branch must be recreated from a fresh backup, not migrated again.

## Running the importer

`pnpm import:assistant` (`import:assistant:prod` for the production profile) is an offline CLI. It reads the frozen profile configuration (owner, timezone, briefing times, weather, imported-preference selection) and compares a document with it; it writes none of that configuration.

```bash
pnpm import:assistant --db <private-db> --file <document.json>                 # validate only: the same code as --apply, rolled back
pnpm import:assistant --db <private-db> --file <document.json> --verify        # counts-only comparison with what is stored
pnpm import:assistant --db <private-db> --file <document.json> --backup <backup.db> --apply
```

`--apply` refuses unless all of the following hold: the database, document and backup are outside this repository; the document is `0600` in a `0700` directory; the backup passes SQLite's integrity check and has the same row count as the live database in every table right now (take it with `pnpm backup`, with the coordinator stopped, immediately beforehand); the database has no pending migrations; the shared runtime lock can be taken, which it cannot while a live coordinator holds the database; and every rule of the importer passes. Output is counts and rule names. Exit codes: 0 passed; 2 refused before the document was read (paths, permissions, configuration, schema); 3 the document or backup was refused; 4 a live process holds the database.

The lock is taken first, for a dry run as well as an apply, and before the backup is looked at; and the backup is compared by the CONTENT of every table (a digest compared in memory and never printed), not by row counts. Document, database and backup are each judged by where their real path lands, so a symlink into this checkout is refused, and each must be mode `0600` in a `0700` directory.

A rehearsal uses a separate, disposable database with the mock transport and no Discord token. The importer is not a rehearsal of Discord delivery and says nothing about it.

## Import invariants

- Validate the whole interchange document before writes. Enforce existing owner, allowlist, length, state, capacity, recurrence and temporal bounds. Fail closed on conflicts or unsupported values; no partial import.
- Import under one target transaction while that profile's coordinator is stopped. The importer takes the shared runtime liveness lock and refuses while a live coordinator holds it; an acknowledgement flag is not proof. Mint collision-checked Ducky public handles. Stable source IDs remain in a private correlation ledger with a unique namespace, category and ID key, in the same transaction and backup. Do not use expiring idempotency keys for durable correlation.
- Protect correlation from ordinary retention. Deletion and Forget leave an identity-only tombstone, without content or a content digest, so repeated import never resurrects a record deliberately removed by the owner. While a record exists the ledger keeps a fingerprint; a later export that changed a correlated record is a counted conflict, never an ignored update.
- Preserve closed state, timestamps, deadlines, reminder settings and cursors and already-delivered checkpoints. Settled occurrences must never become pending sends. Re-import must add zero rows, advance zero checkpoints and introduce zero new notifications, even after target edits, delivery or deletion.
- Compare preferences with frozen runtime config; do not write config or import settings as permissions. Unsupported active settings are refused.
- Watch transition: imported typed checkpoints and settled event identities are preserved, a target without a baseline and a surface that was only partly read are explicit states, and the first observation reconciles from the last known checkpoint across the stopped-notifier window before advancing. Delivery stays stopped for that window; suppressing a baseline message alone does not satisfy checkpoint preservation.
- Report counts and pass/fail field parity only. Never log titles, IDs, deadlines, repository names, preference values, source errors containing data or credentials. Keep exports and evidence files 0600 in 0700 private directories.

## Ordered operator gates

1. Complete the private semantic mapping against the live source and the audited behavior contract. Verify every relevant source field and checkpoint has a destination. Preserve unrelated academic features and identify the assistant module's own controls; do not stop the entire bot.
2. Take a fresh, consistent live-source backup plus separately protected external configuration needed to restore it. Restore in a separate private scratch location, compare integrity/schema/counts and record academic health. The supplied snapshot rehearsal is not a substitute for this gate.
3. Select an explicit target profile/database, stop that coordinator and back it up with `pnpm backup --profile <profile> --db <private-db> --out <private-backup-directory>`. Check the source selection privately before invocation; verify with `pnpm backup:verify --file <private-backup>`. Keep credential backups separate. Never use a default backup directory inside the worktree for private migration evidence.
4. Perform a rehearsal import in an isolated private scratch database with mock transport and no Discord token. A database containing imported real records must never run with real transport during development. Validate counts/fields, repeat import, deadlines, completed suppression, resync and checkpoint reconciliation. Retention defaults off; if enabled, account for its configured windows before and after an observation tick so imported history is not silently pruned.
5. Use a separate, synthetic-only development database for an authorized live server reminder and real Done/Edit/Snooze/non-owner-button check. Neither bot may emit imported reminders during this check. Do not claim a mock transport establishes Discord delivery. Establish a rollback bridge before cutover: demonstrate replay of Ducky-side completion/edit/snooze/delivery/checkpoint deltas into the source through supported private boundaries, with no repeated notifications. If that bridge is unavailable, cutover remains blocked; do not accept silent loss.
6. Only after rehearsal migration, notification and rollback verification pass, arrange an operator-controlled cutover window. Pause assistant-only writes and notifier, leaving academics available. With both notifiers stopped, take a final consistent source snapshot/export including any deliveries or completions since rehearsal. Back up the stopped target, import that final export, verify counts/owner/checkpoints, and prove no old notifier remains active before starting Ducky delivery. Observe an authorized due reminder and duplicate-free notification/watch ticks. No production import from a stale rehearsal export.
7. If failure occurs before Ducky accepts writes or sends anything, stop Ducky and restore its pre-import target backup with downtime using `docs/runbooks/backup-and-restore.md`, then resume the unchanged source module. If Ducky has accepted writes or delivered, first freeze both sides, take the private delta with `pnpm export:rollback-delta` (stopped coordinator, or a verified backup; exit 0 only, never a file written with `--allow-incomplete`), and apply/verify the rehearsed reverse-delta bridge, including delivery checkpoints, before re-enabling the old module. The export is read-only and is not the bridge: a delta whose `complete` is false, or whose deletions include cause `unknown`, must not be applied, and history already lost is not reconstructible. Run the export BEFORE any retention pass can prune finished records. A backup that passes the export's liveness check is not thereby the final or latest one (an older backup from a stopped coordinator passes too): that the delta was taken from the final state remains operator evidence. Do not merely restore stale data and resume reminders. Retain both backups and prove the source backup still restores. There is no bulk-delete rollback.
8. After a stable owner-approved observation period and academic health check, remove only the old private-assistant module in its private repository, with its own review and recoverable backup. This public repository contains neither that deletion nor private source. Until this gate passes, retirement is incomplete.
